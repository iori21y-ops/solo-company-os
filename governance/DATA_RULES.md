# 데이터 창고 기준 (v0.1 초안, 2026-11-10 — 사장님 확인 전)

> 목적: 어떤 주제든 "주제를 정한다 → 필요한 데이터를 모은다 → 글·쇼츠·영상을 만든다"가 같은 순서·같은 형식으로 돌게 하고, 사장님이 데이터 현황과 구조를 직접 볼 수 있게 한다.
> 중심 원칙: **쓰이는 것만 남긴다.** 더 많이 모으는 기준이 아니라, 모은 것이 콘텐츠와 상담으로 이어지는지 보는 기준이다.
> 폴더·저장 위치 규칙은 `FOLDER_RULES.md`, 수집기 출력 규칙은 `cadam/collectors/COLLECTOR_CONVENTION.md`. 이 문서는 그 위에 "데이터 한 건을 어떻게 적고, 언제 늘리고 줄이나"를 정한다.
> 화면: `python3 ~/projects/_meta/dashboard/build.py --open` → 사업별 데이터 탭.

## 1. 창고는 두 층이다
| 층 | 무엇 | 어디 |
|---|---|---|
| 숫자 창고 | 표·숫자·추세·이력 | 사업별 DB (렌테일러: 로컬 PostgreSQL `cadam`의 warehouse·data, 해외파: `_data/football/work/football-blog/warehouse.sqlite3` → 추후 PostgreSQL `football`) |
| 맥락 창고 | 배경·경과·기사에서 뽑은 사실·사람이 읽는 설명 | second-brain 위키(렌테일러), brain 페이지(해외파) |
| (노출값) | 사이트가 바로 읽는 값 | Supabase — 창고의 사본이 아니라 "사이트용으로 내놓은 값"만 |

두 층은 **연결 열쇠**로 잇는다: 렌테일러는 차종 이름표(`vehicle_name_map`), 해외파는 구단·선수 통일 ID(`clubs`·`players`). 새 데이터는 이 열쇠에 연결되지 않으면 창고에 넣지 않는다(연결 안 되는 데이터는 글에서 다른 데이터와 합칠 수 없다).

## 2. 데이터 명세 — 데이터 하나마다 적는 항목
각 사업의 데이터 목록 원본(렌테일러 `monitoring/data_catalog.py`, 해외파 `datacheck.REGISTRY`)에 한 줄씩 적는다. 대시보드는 이 목록을 읽어 그린다.

| 항목 | 내용 | 지금 |
|---|---|---|
| 이름 | 사람이 읽는 이름 | 양쪽 있음 |
| 표 | 저장된 표 이름 | 양쪽 있음 |
| **카테고리** | 주제별 분류(§3) | **없음 — `_meta/dashboard/data_categories.yaml`에 제안, 확정 후 목록으로 옮김** |
| 구분 | 계속 수집 / 1회 수집(고정) / 파생(우리 코드가 만듦) / 사본 | 양쪽 있음 |
| 출처·수집기 | 어디서, 어느 예약 작업이 | 양쪽 있음(형식 다름) |
| 주기·허용 지연 | 얼마나 자주, 며칠 늦으면 경고 | 양쪽 있음 |
| **이용 등급** | A 자체 수집·공공·승낙 / B 출처 이름 없이 통계로만 / C 약관상 회색(사장님 결정으로 수집) / X 사용 금지 | 렌테일러만 있음(✅🔒⏸⛔). **해외파는 없음** |
| 점검 | 신선도·행 수·정합성 중 무엇을 보는지 | 양쪽 자동 점검 있음 |
| **쓰는 곳** | 어느 콘텐츠·페이지가 쓰는지 | 코드 검색으로 추정만 — §5 사용 기록으로 대체 |

## 3. 카테고리 (주제별, 사업별로 따로)
- 렌테일러 11개: 렌트료·견적 / 차량·가격표 / 혜택·출고 / 판매·등록 / 중고·감가·승계 / 보험·안전·리콜 / 전기차·연료 / 금융·물가 / 렌터카 업계 / 뉴스·검색 수요 / 유입·성과
- 해외파 6개: 경기·순위 / 선수 기록 / 이적·시장가치·연봉 / 감독·구단 / 이름·ID 통일표 / 채널 성과
- 카테고리마다 "이 자료로 만드는 콘텐츠"를 적는다(렌테일러는 개편 계획의 시리즈·트래커와 연결). 만들 콘텐츠가 없는 카테고리는 정리 검토 대상이다.
- 목록에 있는데 카테고리가 없는 데이터는 화면에 '미분류'로 나온다.
- **콘텐츠 연결표**: 계획된 글(심층 시리즈·트래커·뉴스)마다 쓰는 데이터를 적는다(`data_categories.yaml`의 `content`, 출처는 개편 계획 문서). 화면은 이걸로 ① 카테고리별 "이 자료로 만드는 콘텐츠" ② 글마다 필요한 데이터의 지금 상태 ③ 읽는 코드도 계획된 콘텐츠도 없는 데이터를 보여 준다. 글 계획이 바뀌면 이 표도 같이 고친다.

## 4. 늘리는 규칙과 줄이는 규칙
**새 데이터·수집기를 만들기 전에** 아래 네 가지를 적는다. 하나라도 비면 만들지 않는다.
1. 어느 질문(고객이 궁금해하는 것)에 답하는가
2. 어느 콘텐츠(글 시리즈·트래커·쇼츠·사이트 페이지)에 쓰는가
3. 이용 등급(약관·출처 표기 조건)
4. 연결 열쇠(차종·선수 ID)에 이어지는가

**줄이는 규칙**: 석 달 동안 어느 콘텐츠·페이지에도 쓰이지 않은 데이터는 분기마다 목록을 사장님께 보이고 ① 쓸 계획을 정하거나 ② 수집 주기를 늘리거나 ③ 수집을 멈춘다(데이터는 지우지 않고 보존).

**핵심 상품과 AI 학습 재료는 A·B 등급으로만** 만든다. C 등급은 참고·보조로만 쓴다.

## 5. 기록 — 나중을 위해 버리지 않는 것
| 기록 | 왜 | 지금 |
|---|---|---|
| 과거 값 이력(스냅숏) | 추세·변화가 콘텐츠가 됨 | 대부분 있음 |
| **사용 기록**: 콘텐츠 한 편이 어떤 데이터의 어떤 숫자를 썼나 | "쓰이는 데이터"를 사실로 알기 위해, 숫자 검증, 수정 추적 | **없음 — 만들 것**(글 상태 파일에 `data_used` 칸) |
| 승인·반려·수정 기록 | 품질 기준을 배우는 재료 | 부분(디스코드 승인, 글 상태 파일) |
| 성과: 조회 → 사이트 유입 → 상담 | 무엇이 상담을 만드는지 | 부분(유입 수집 중, 상담 연결 없음 — REN-138) |

## 6. 새 주제를 붙이는 순서
1. 주제와 고객 질문 정하기 → 2. 필요한 데이터 목록(있는 것 / 없는 것) → 3. 없는 것만 §4 네 가지를 적고 수집기 추가, 명세 한 줄 등록 → 4. 점검 등록(새 표는 점검 목록에 한 줄) → 5. 엔진에 내주는 창구 함수 → 6. 콘텐츠(자료 묶음 → 글 → 파생: 네이버·쇼츠·영상) → 7. 사용 기록·성과 확인.

## 7. 아직 정하지 않은 것 (사장님 확인 필요)
- 카테고리 이름과 분류(§3, 화면에서 보고 고칠 것)
- 줄이는 규칙의 기간(석 달)과 보는 주기(분기)
- 해외파 데이터의 이용 등급 표기(트랜스퍼마르크트·FBref·Capology는 C로 적을지)
- 사용 기록을 어디까지 남길지(표 단위 / 숫자 단위)
